   （不光 Unit，Building 这条是必炸的死循环）

3. **两套 Building 并存**：手写的 `type/Building.java`（`extends Entity<EntityType, Building>`，仍被
   Turret/BlockRender/存档/`World.setBuilding`/MenuFragment 使用）和生成的 `base.ecs.Building`
   （只有工厂生产它）。`BuildingType` 里保留 `block` 字段作为"过渡桥"，作者注释说等 Block 实现
   EntityType 后拆掉。
4. **池只进不出**照旧：`create` 用 `Pools.obtain`，Unit/Building(新) 都没有 `Pools.free`

### 踩到的坑（重要）

**`@Import` 借不到 `Entity.type`**：基类它是泛型字段 `T`，ECProcessor 校验严格，
组件里写 `public BuildingType type` 会报
`@Import field 'type' has type BuildingType, but the borrowed field has type T`。
这是**实体级错误** → 整个 Building 不生成 → 满屏"找不到符号 类 Building"，极容易误判成别处的问题。

> 教训复发：09-24 就说过「ECProcessor 报错会让 base.ecs 包整体消失」，这次又撞一次。
> 排查时永远先看注解处理器那几条 error，"找不到符号"全是连锁反应。

绕法：需要用 type 的逻辑放进 `BuildingType.rebuild(Building)`，
由 DataIO 在 `b.read(r)` 之后显式调用 `type.buildingType.rebuild(b)`
（按恢复出的 angle 重算 shapeOffsets / 中心坐标 / maxHealth / teamData —— 这些都是派生数据）。

另外 grep 时踩了个小雷：`WorldData.buildings` 里是**小写** b，
大小写敏感搜 `Building` 会漏掉 TeamData 那处，得两个形式都搜。

### 已修（第二次 round）：UnitType.remove / 对象池回收

用户一句「那就先改」，接着上一轮的遗留做掉。

  没有声明初始化式的运行时字段必须显式托底，否则上一个单位的残留串下一个身上。

### 两个关键发现（写进 main.txt 和 MEMORY.md 了）

1. **这条路径会被 BulletProcess 线程直接触发**：`Entity.applyDamage` 血量归零就 `kill()`，
   **不走** freshKills 那条「登记 → 主线程 drain」的延迟通道。所以摸 `moveunits` 必须持它原有的锁
   （UnitMath:30/38/142 和 InputProcess:289/314 都在用 `synchronized (WorldData.moveunits)`）。
2. **同一单位会同时进 `deadUnits` 和 `freshKilled`** → 会被 kill 两次 → double-free 池。
   用 `u.type == null` 挡（`Pools.free` → `reset()` 会把 type 置空）。
   顺带发现 HUDFragment:196-203 那层 UI 兜底是在对象回池**之后**才摸 `u.isSelected`，
   那时 u 可能已被复用成别人；remove 里即时摘掉 checkedUnits 正好把这个隐患堵上。
