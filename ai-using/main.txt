## 项目概览

一款基于 Arc 框架（Mindustry 底层引擎）的 RTS + 自动化多平台游戏。

- 作者：caliniya（AKA 十一舰队）
- 引擎：Arc v157.1 (https://github.com/Anuken/Arc)（具体版本去看构建脚本）
- 语言：Java 17
- 构建：Gradle 8.10 多模块
- 规模：主源码约 19.6k 行（core 107 个 java 文件）

## 编译期 ECS（整个项目最有分量的设计）

注解全部 `RetentionPolicy.SOURCE`，运行期零开销。

- 注解集（`annotation/.../Annotations.java`）：`@Component(name, proc, index)`、`@Entity(comps, name, type)`、`@SystemDef(name, thread, index)`、`@ThreadDef`、`@Updata`、`@Save(index)`、`@Import`（借其他组件或 Entity 基类的同名字段，不重复注入）、`@OverrideEntity`、`@Write`/`@Read`
- `ECProcessor` 生成 `caliniya.vergvoke.base.ecs` 包下的三个类，产物在 `core/build/generated/sources/annotationProcessor/java/main/`：
  - `Unit.java` —— 实体类，由 `@Entity` 的组件字段拼出来，继承 `Entity<UnitType, Unit>`
  - `EntityArs.java` —— 每种实体一个 `EntityAr` 容器（目前只有 `Unit`）
  - `Systems.java` —— 系统总览 + `updateAll()` 帧序驱动
- `SystemProcessor` 只做校验：系统名唯一、thread 合法、index 线程内唯一、组件 index 在实体内不能撞、`@Updata` 方法必须且只能有一个 `float delta` 形参、组件字段名不能在实体里重复
- `AutoProcessor`（tools 模块）扫 `@AnnoProc` 自动生成 META-INF/services SPI，省得手维护
- **2026-10-03 ECProcessor 增强**：组件方法**全量注入**——不再只挑 public，private/protected/包私有/static 辅助方法都铺进生成实体并保留原修饰符（与 Entity 基类同签名的方法直接报错并提示用 `@OverrideEntity`）；组件**字段初始化表达式跟到生成实体**（initializerOf，`public float speed = 5f` 会正确出现在生成类里——但对象池复用不走字段初始化，create 里必须显式托底）；组件 import 原样搬进生成文件，方法体里可直接用 Mathf/Entities 等短名

**固定帧序**（`Systems.updateAll`）：`e.sync(delta)`（热量/能量/能力/模组）→ 组件系统（按 index）→ `e.update(delta)`。

`system/System<T>` 基类支持主线程 / 独立线程两种模式：线程模式自带 60 TPS 控制、TPS 平滑统计、暂停锁、`EventType.GamePause` 响应。

当前已声明的东西：
- 唯一 `@SystemDef`：GameProcess（thread=main, index=5）
- `@Entity`：UnitDef（StateComp / MoveComp / WeaponComp / TargetComp）、BuildingDef（BlockComp / TargetComp / TurretComp，type = `BuildingType`，工厂在类型上）
- 组件 index：State=1、Move=2、Block=3、Target=4（Unit+Building 共用）、Weapon=5、Turret=6
- **索敌组件化（2026-10-03）**：索敌从 EntityProces 线程迁出，现在 `TargetComp` 的 `@Updata` 随主线程实体更新跑（失效立即重搜 + 按 retargetInterval 周期重搜，可挂 filter）；`WeaponComp.updateWeapons` 开头做武器级锁敌（旋转武器失效/超射程 → `w.type.findTarget`，固定武器直接用单位 target）；Turret（建筑）失效/超射程自取目标。EntityProces 现在只剩存档写入状态机。索敌半径在 `UnitType.create` 取武器最大射程写入 `TargetComp.range`
- **`@Import` 借不到 `Entity.type`**：基类那个是泛型字段 `T`，处理器的类型校验过不去（`...has type XxxType, but the borrowed field has type T`）。
  实体级错误会直接让整个 `@Entity` 不生成 —— 表现为满屏"找不到符号 类 Building"，根因是组件里那一条。
  需要用 type 的逻辑（例如读档后按 block 配置重算派生数据）一律放到 XxxType 侧的方法里，由调用方显式调用。

**手写系统**（不通过注解，靠 `Data.loadSystems()` + `Data.enter()` 手动装载）：
- 主线程、并入 `Systems.systems` 排序数组：GameProcess(5)、Render(9)
- 并入 `Render.renders` 管线数组（不算独立系统）：MapRender(10)、BlockRender(12)、UnitRender(13)、UniverseRender(16)、DebugRender(14, 目前注释掉没启用)
- 独立线程：`init()` 自带循环：BulletProcess、UnitMath、EntityProces（索敌已迁出，只剩存档写入状态机）

## 主循环

`Vergvoke.update()`：资源没加载完 → 画加载界面；加载完 → `platformInput.update` → `Game.update(delta)` → `if (Game.inGame) Render.it.update(delta)` → `camera.update()` → `scene.act/draw`。

**delta 钳制与焦点暂停（2026-10-03）**：`Vergvoke.init` 里 `Time.setDeltaProvider` 把 delta 钳到 ≤10 帧——不钳制则截图/焦点切换后的巨帧把移动单位一帧甩出地图。`Game.focusPaused`（Vergvoke.pause/resume 维护）在 `Game.update` 门禁冻结主线程模拟；背景线程由 System 基类响应 `GamePause`（isPausable 的才挂起）；渲染/UI 不冻结（可截图）。主循环是唯一 delta 消费点。

`Game.update` 只在 `Game.inGame` 为真时调 `Systems.updateAll(delta)`。`Render` 同样只在游戏内跑（相机 clamp 和星图渲染都需要游戏内数据）。

进游戏的路径：`Data.load(file)` → `GameIO.load` → `DataIO.load`（IO 线程读档，`Core.app.post` 回主线程）→ `Data.loadSystems()` + `Data.enter()`。`Data.enter()` 里才给 `Game.starMap` 赋值、置 `Game.inGame = true`、切 `UI.Game()`。

**注意时序**：`WorldData.initWorld()` 在 post 之前就跑，`Game.starMap` 在 post 之后的 `enter()` 才有值，中间存在「world 非空但 starMap 为 null」的窗口，任何每帧无条件读 `Game.starMap` 的代码都会炸。

**重载生命周期（2026-10-03 修复）**：`Data.loadSystems` 先 `Events.fire(ThreadedStop)` 停旧后台线程（`System.init` 里注册的 stopThread 幂等；不 fire 就线程泄漏，旧子弹线程会把陈旧缓冲换进双缓冲 bullets，表现为重载后子弹渲染错乱）→ `Systems.systems.clear()`（旧主线程系统实例不清会被 updateAll 双驱动）→ 创建新实例 → `WorldData.rebuildTransientContainers()`（重建 moveunits/bullets + `Entities.clearDead()` + `initAllTrees` 重刷四叉树）。已知未修：旧 MapRender 区块纹理不 dispose，每次重载漏一点 GPU 内存。

## 内容体系

`Contents` 按 `CType` 分类存数组 + 名称映射，ID 从 1 起，`getByID` O(1)。加载顺序 Items→Liquids→Floors→ENVBlocks→Blocks→Units→Enhancements→Stars→各 `load()`→Techs。

`type/` 与 `content/` 的关系：`content/Xxx.java` 是静态注册清单，`type/type/XxxType.java` 是类型类（配置 + 类型级行为）。`EntityType` 接口把两者接起来：`create(team, x, y)` / `sync` / `update` / `draw` / `kill` / `remove`。
目前实现者是 **`UnitType` 与 `BuildingType`**。方块经 `Block.buildingType` 反向持有自己的 `BuildingType`
（这也是当前的"过渡桥"：`BuildingType.block` 供 size/psize/health/形状，等配置搬进 type 后这层拆掉）。

伤害结算三层：能力拦截（护盾）→ 护甲（倍率 × 抗性 − 强度）→ 本体。护盾体系是 `Ability` / `Shield` / `ForceField` 三件套；Enhancement（增强）是纯数据，行为在 `EnhancementType`，目前唯一实现是 `ShieldBoostEnhancementType`。

## 世界 / 宇宙

- `World` 按区块（`WorldChunk.SHIFT/MASK`）存地板 / 环境方块 / 建筑，TILE_SIZE=32
- 实体容器唯一权威是生成的 `EntityArs.Unit` / `EntityArs.Building`（static final，带 `e -> e.id` 提取器，`WorldData.initWorld` 里 clear 重置）；WorldData 自己只持 `RouteData` 导航（`moveunits` 是 UnitMath 的寻路队列、`bullets` 是子弹双缓冲容器）
- **建筑生命周期门面（WorldData，全项目唯一写入口，2026-10-03 定案）**：`placeBuilding`（BuildingType.create 纯构造 → placeTiles 占位/覆盖拆除/导航 updateBlock → 容器 add）、`removeBuilding`（幂等，导航清占必须在瓦片注销前 → unregisterTiles → 容器 → freeID → 回池）、`syncTree`（「改坐标必 EntityArs.move」铁律的唯一执行点）、`setEnvBlock`、`mapLoaded`（读档瓦片装载完后重刷 RouteData.init，修了「读档后固体装饰不进导航图」）。职责划线：World=纯瓦片层、BuildingType=纯构造+派生数据、RouteData.updateBlock 只许门面调
- `RouteData`（~1200 行，2026-10-03 整体重写为 **HPA\***，是除 ECS 外第二复杂的模块）：地图切 10 格 chunk，相邻 chunk 公共边界每段连续可通行取中点一个「门口」（段数>2 只留首尾）；`ChunkNav` 缓存门口两两之间的 chunk 内路径（octile cost + minClear 体积注解）。`findPath(sx,sy,tx,ty,unitSize,capability)`：同 chunk 直接局部 JPS（findPathDirect），跨 chunk 先把起终点连到本 chunk 全部门口，门口抽象图上 A*（按 minClear 过滤），addSeg 拼接去重 + smoothPath 收尾。元素惰性创建（markNavDirty 对 null 跳过；ensureClean 在 rebuildLock 内建好原子换槽），`ChunkNav.dirty` 是 volatile 保证并发发布；clearance = Chebyshev 距离（8 邻域，斜角不穿角）；寻路 scratch 全 ThreadLocal（代际戳免全量清理、IntFloatMap 消装箱）；小图（≤30 万瓦片）导航更新全量重算、大图有界泛洪 ±24（已知近似：放墙过度封锁、拆墙保守绕路）。调试可视化：MapRender.drawNavDebug（chunk 网格/门口/边路径，配 RouteData.debugWarmChunk 预热）
- `world/stars/`：StarMap / StarNode / StarRoad，节点和航路各一棵四叉树，`write/read` 序列化写得很完整（邻接只由 id 小的一侧 link 防重复边）

## 存档

全部自研二进制（不是 json），带 MAGIC：`AEVS`(GameIO/DataIO)、`AESS`(WorldIO)、`AEVP`(ProgressIO)；实体后写 8 字节 `0xAE` 结束标记。**SAVE_VERSION=2（2026-10-03，读取校验版本，旧档拒载）**：单位序列化补 `isSelected`、team（byte ordinal，-1=null，经 StateComp 的 @Write/@Read——@Save 不支持枚举）、targetX/targetY/x/y；建筑走 `create → read → rebuild → placeBuilding(b)` 门面，DataIO 读档在瓦片装载完调 `WorldData.mapLoaded()`。已知：建筑序列化不含 id（读档重新分配）。

数据目录由 `io/DataPaths` 三级解析：`-Dvergvoke.datadir` → `<程序目录>/data`（带写探针）→ `%APPDATA%/Vergvoke` 兜底。desktop 的 run/debug 固定到 `build/run-data`。
