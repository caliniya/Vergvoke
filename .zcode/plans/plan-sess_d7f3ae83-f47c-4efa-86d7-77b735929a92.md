# 用 Ar 家族全面替换 Seq(Arc fork + 游戏侧 + 删 tools 克隆)

## 已确认事实(探索结论)
- 游戏代码已基本全用 Ar(tools 版),Seq 只剩 `tools/IconGen.java` 3 行;arc fork 内部 Seq 是签名级 API(137 文件/约 1280 处)。
- Ar≈旧版 Seq 改名:行为差异仅 `set()` 缺自赋值保护;缺 `map(T[],Func)/groupBy/groupByCount`;多 `toSeq()`;javadoc 被全局替换弄坏。
- ObjectSet 克隆 = 老 libGDX 布谷鸟哈希,与 arc 现行 Fibonacci 版算法不同,替换需合并便利方法。
- 游戏侧不用 arc Json;IntAr/FloatAr 游戏侧零使用;StarMap 的双 ObjectSet import(单类型优先)在 tools 删除后自然收敛到 arc 版。
- ECProcessor 生成模板(:1814)和处理器自身(:17-18)引用 `caliniya.vergvoke.base.tool.Ar/ObjectSet`,必须同步切到 arc 包。

## 实施步骤

### 一、arc 子模块准备
1. `arc/` 当前是 detached HEAD——先在 submodule 里建分支(如 `ar-container`)再动任何文件。

### 二、Ar 家族搬进 arc(先补齐,再替换)
2. 把 `tools/.../base/tool/{Ar,IntAr,FloatAr}.java` 搬入 `arc/arc-core/src/arc/struct/`,包声明改 `arc.struct`:
   - Ar:删 `toSeq()` 与 `arc.struct.*` 自引用;`asSet()` 改用同包 ObjectSet;mapInt/mapFloat 自然指向同包 IntAr/FloatAr
   - `set()` 补 `if(array == this) return;`
   - 与现行 Seq/IntSeq/FloatSeq 逐个 diff,把 arc 版多出的方法补进克隆版(Ar 已知缺 3 个;IntAr/FloatAr 缺什么以 arc 内部实际调用为准),移植时按克隆版风格写
   - 顺带修 javadoc 里被替换坏的词(Aruence→Ar 等),不追求完美
3. **ObjectSet**:以克隆版(布谷鸟)为基底替换 `arc/arc-core/src/arc/struct/ObjectSet.java`(同名直换),合并 arc 版便利方法:`copy()/find(Boolf)/any()/notEmpty()`、`addAll` 返回 boolean、拷贝构造泛型通配 `<? extends T>`;删死 import AssetDescriptor。编译后验证 `OrderedSet`(extends ObjectSet,内部直接摸 keyTable)兼容——这是本步最大风险点,编译+遍历行为都要过。

### 三、arc 内部全量替换(脚本化,脚本放 ai-using/src/temp/)
4. 词边界正则替换:`FloatSeq→FloatAr`、`IntSeq→IntAr`、`Seq→Ar`(**先保护 CharSequence**——负向断言 `(?<!Char)Seq\b` 或先占位再还原),范围 `arc/arc-core/src` + `arc/backends`,含:
   - 文件改名:Seq.java/IntSeq.java/FloatSeq.java/SnapshotSeq.java/DelayedRemovalSeq.java → Ar/IntAr/FloatAr/SnapshotAr/DelayedRemovalAr(内容用第 2-3 步的合并版,原文件删除)
   - 子类/引用自动跟随:Jval.JsonArray extends、Json.java 的 `Seq.class` 特判、`Pools.obtain(Seq.class)`、方法名 toSeq→toAr 等
5. 复查 grep:arc 内无 `Seq` 类引用残留(排除注释/字符串里无辜词);无 `CharAr` 之类误伤;字符串字面量/反射里搜 `arc.struct.Seq`。
6. 编译 arc:`./gradlew classes`(主仓库触发 includeBuild)或进 arc 单独构建,红则修。

### 四、游戏侧切换(脚本化)
7. 全仓库(排除 arc/)把 `caliniya.vergvoke.base.tool.{Ar,IntAr,FloatAr,ObjectSet}` 的 import 换成 `arc.struct.*` 对应类:
   - 显式 import Ar 的 ~18 个 core 文件 + annotation 5 个文件
   - 通配 `import caliniya.vergvoke.base.tool.*;` 的 5 个文件(Entity/Render/GameProcess/MoveComp/UnitType)→ 改 `import arc.struct.*;`(注意已有 arc.struct 通配 import 的文件可能冲突,逐个看)
   - StarMap:删 `base.tool.ObjectSet` 单类型 import(通配自动接管);ECProcessor :17-18 与生成模板 :1814 改 arc 包
   - tools/IconGen.java 3 行 Seq → Ar
8. 删除 tools 模块四个克隆类文件。
9. 全仓库 grep 复查:`base.tool` 容器引用零残留;`arc.struct.Seq` 零残留。

### 五、验证与收尾
10. `./gradlew classes` 全绿 → `./gradlew dist` 出 fat jar。
11. arc 子模块:在分支上提交;提醒你推送到 fork 后主仓库 `git add arc` 更新 gitlink(我不主动推远端)。
12. 更新 ai-using/main.txt:tools 模块描述(容器已随 fork 走)、给 AI 注意事项里「Ar 命名有意为之」条目调整;更新我的持久记忆(arc 迁移条目追加 Ar 替换事实)。

## 风险与已知取舍
- OrderedSet 与 ObjectSet 内部耦合是最大风险,单独编译验证。
- 迭代顺序/hashCode 与 arc 旧版不同(布谷鸟 vs Fibonacci)——游戏不依赖 arc Json/序列化,影响面仅 arc 内部(Textures packer/Settings 等),可接受。
- fork 与 Mindustry upstream 的差异进一步加大,以后同步 upstream 更难——按你"自己维护 fork"的方向已接受。
- 替换后游戏代码 import 仍写 `arc.struct.Ar`,IDE 端 VS Code 的"无法解析 arc"告警是无害已知项。
